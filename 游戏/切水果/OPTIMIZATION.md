# 手部追踪切水果：优化方案与技术栈

## 交互目标与本次实现

默认流程是「看见手 → 追踪手掌中心 → 移动刀片 → 移动轨迹切果」。无需先识别某个手势指令。

- 位置由手腕与四个指根的平均值确定，排除指尖，减小手指屈伸对控制位置的影响。这是项目中的控制锚点设计，不是 MediaPipe 输出的额外关键点。
- 屏幕显示刀片，刀尖光圈的位置与碰撞检测坐标相同，朝向跟随移动方向。
- 伸指、捏合是可选的切果开关；关闭开关时，刀片仍然跟着手移动，只是变暗并停止切果。
- 丢手、断流与重新起刀时切断轨迹，防止恢复识别后从旧位置横扫屏幕。
- 已完成动态平滑、两点标定、分段性能诊断、事件推送、对象复用和独立环境启动。打包、双人玩法及跨设备体验验收仍在后续范围。

## 当前技术栈

| 层 | 技术 | 项目中的职责 |
| --- | --- | --- |
| 摄像头 | Python + OpenCV | 摄像头采集、切换、重连、预览图像 |
| 手部追踪 | MediaPipe Tasks HandLandmarker，VIDEO 模式 | 手部关键点和帧间跟踪 |
| 控制处理 | Python 几何计算 + One Euro / EMA | 手掌锚点、可选捏合/伸指、动态平滑、轨迹编号 |
| 本地服务 | aiohttp + WebSocket | 提供页面、设置、状态、最新坐标消息 |
| 游戏 | Phaser 3 + JavaScript | 折线路径碰撞、水果对象池、粒子复用、玩法和声音 |
| 设置界面 | HTML / CSS / 原生 JavaScript | 预览、两点标定、分轴映射、调参、暂停和性能诊断 |
| 数据 | JSON + localStorage / 内存回退 | 识别设置、个人映射、浏览器偏好和排行榜 |
| 部署 | venv + 已验证依赖版本 + 设备文件锁 | 独立环境、同项目服务复用、避免重复打开摄像头 |
| 验证 | unittest + Node test + Playwright / Edge | 算法边界、通信、浏览器流程 |

MediaPipe 的 VIDEO 模式已经利用跟踪来减少重复的掌部检测；不需要为了「追踪手」再单独训练一个手势分类网络。[官方 Python 文档](https://ai.google.dev/edge/mediapipe/solutions/vision/hand_landmarker/python)

## 已实施并验证

| 方案 | 实现与验证结果 |
| --- | --- |
| 分段测量 | 使用 perf_counter 记录最近 180 个样本的 P50/P95；界面显示采集、推理、预览、处理、等待推送指标；停止出帧时报告异常 |
| 动态平滑 | 默认 One Euro，保留 EMA 对照；固定合成轨迹静止抖动降低约 25%，运动误差降低约 48%；15/30/60Hz 测试停止后无过冲 |
| 操作范围标定 | 两个角点稳定采样、横纵独立缩放、个人映射保存/恢复；无手或无效范围不覆盖已有映射，浏览器回归通过 |
| 部署稳定性 | ASCII / CRLF 启动脚本、项目 .venv、版本锁定、端口提前预留、同项目复用、摄像头跨进程锁；真实 cmd 启动和重复启动通过 |
| 减少发送等待 | 结果到达即唤醒推送，最新帧邮箱、消息序号、去除骨架载荷；独立环境摄像头复测约 30 FPS，等待推送 P50/P95 为 0.19/0.33ms |
| 轨迹正确性 | 单个渲染帧内保留折线，丢包、积压、丢手、切设置和窗口缩放断线；避免把转弯路径简化成跨越炸弹的直线 |
| 长期运行基础 | 水果池上限 48，粒子复用且有上限；15 次重开后再真实运行 180 秒，切果 2378 个，发射器和物理对象未持续增长 |
| 交互异常恢复 | 暂停冻结连击时钟、切后台暂停、预览关闭时取消请求、排行榜损坏数据过滤、存储不可用时会话内保存 |

上述滤波改进来自固定种子的合成轨迹，发送耗时只覆盖服务端结果等待发布，均不能等同于真人手到屏幕的端到端延迟。测试详情见 [TESTING.md](TESTING.md)。

## 下一阶段方案

| 优先级 | 方案与技术 | 解决的问题 | 验收方式 |
| --- | --- | --- | --- |
| P0 | 真人手感与不同设备采样 | 合成数据不能证明不同身高、肤色、姿态、距离和光照下的实际体验 | 现场标定后覆盖四角，重复快速折返、停手、遮挡再入场；记录误切、漏切与主观延迟 |
| P0 | 30 分钟展台持续运行 | 本轮 180 秒压力检查不足以证明长时间稳定 | 同时监测对象数量、堆内存、渲染帧时间和识别帧率；比较预览开关前后 |
| P1 | 采集线程与推理线程分开，队列容量 1 | 推理较慢时相机内部积压旧帧 | 人工增加推理负载，帧龄保持有界；切换摄像头和退出时正确释放资源 |
| P1 | 根据渲染帧时间调整特效质量 | 低性能显卡上粒子和发光可能掉帧 | 保持刀片、碰撞与输入采样质量，仅降视觉特效；测试档位切换不抖动 |
| P1 | PyInstaller 目录式发布，携带模型和前端资源 | 展台电脑不方便安装 Python | 在未安装开发环境的 Windows 机器离线启动、加载模型、打开摄像头 |
| P2 | 双手轨迹关联、独立平滑器和双人计分 | 两个人或两只手控制不同刀片 | 双手交叉/离场再入场时不错误连线、分数归属正确 |

One Euro Filter 会根据速度调整滤波强度，适合先做对照试验；其参数必须依据轨迹数据与现场体验选择，不能保证换算法就一定更快更稳。[算法作者说明](https://gery.casiez.net/1euro/)

本阶段保留一个摄像头/推理工作线程：本机已测到约 30 FPS，尚无充分证据要求增加采集线程和退出协调复杂度。只有在目标设备的采集帧龄或推理积压可复现时再实施拆分。

PyInstaller 可以把 Python 应用和依赖组织为目录或单文件发布；此项目建议先做更便于排错的目录式版本，再验证 MediaPipe 本地库、模型及静态资源是否都被收集。[官方打包说明](https://pyinstaller.org/en/stable/operating-mode.html)

延迟测量应区分时钟：Python 和浏览器的单调时钟起点不同，不能直接相减。服务端阶段各自用同一个单调时钟；浏览器单独测消息到达至渲染耗时。端到端测量可做时钟对齐估计，或使用高速录像记录手部与屏幕的响应。帧率目标与延迟目标均需在目标电脑上建立基线后制定。

## 三种架构路线

| 路线 | 技术组合 | 适用场景 | 主要成本 |
| --- | --- | --- | --- |
| 继续现有架构（优先） | Python + OpenCV + MediaPipe + aiohttp + Phaser | 本机展台、需要摄像头调试和离线运行 | 管理 Python 环境和摄像头所有权；现有代码复用最多 |
| 纯浏览器方案 | @mediapipe/tasks-vision + Web Worker + Phaser | 希望通过网页分发、减少 Python 安装步骤 | 重写采集与识别层；处理摄像头授权和浏览器兼容；离线资源需本地化 |
| 原生 Python 游戏 | pygame-ce + OpenCV + MediaPipe | 必须使用 Python 原生窗口、想把项目收敛为 Python | 需迁移 Phaser 场景、DOM 设置面板与特效；收益取决于部署要求 |

Web 端 HandLandmarker 的同步检测会阻塞调用线程，官方建议可用 Web Worker 把检测移出 UI 线程。纯浏览器不是自动获得更高帧率，仍需在实际设备测量。[官方 Web 文档](https://ai.google.dev/edge/mediapipe/solutions/vision/hand_landmarker/web_js)

pygame-ce 提供图形、输入、声音等游戏开发模块。是否迁移到它属于项目架构选择；当前目录名称中有 pygame 并不代表当前前端使用了 pygame。[pygame-ce 文档](https://pyga.me/docs/)

## 与「刀片跟手」有关的实现约束

1. 保持「位置追踪」和「是否切果」分离，默认只依赖追踪位置。
2. 渲染位置和碰撞位置使用同一条坐标链。若后续加入插值，应同步调整碰撞线段并测试快速挥动，避免出现看到刀片碰到却切不到的情况。
3. 不默认根据过去速度预测未来位置，避免手停下后仍继续出刀；如要试验预测，必须有过冲测量和上限。
4. 30Hz 输入配合高刷新率渲染仍只有约 30 个新位置样本，不能把游戏 FPS 当作识别 FPS。
5. 双手扩展不能只把 `MP_MAX_HANDS` 设为 2。当前单人引擎仍只选一只手，需要额外的身份关联和独立刀片状态；Left/Right 标签也不等于持久的玩家身份。

本阶段已完成可自动验证的单人版优化；下一步优先现场手感与更长时间、多设备测试，再根据测量选择后续架构或打包工作。真实摄像头检查证明采集和模型可用，但没有真人持续挥手的验收记录。
